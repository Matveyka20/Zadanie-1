# Техническое задание: RequestSystem — система обработки заявок

## 1. Общие сведения

**Наименование системы:** RequestSystem  
**Назначение:** автоматизация приёма, учёта, обработки и контроля заявок в организации.  
**Предметная область:** обработка обращений (на примере службы технической поддержки; легко адаптируется под другие типы заявок).  
**Цель:** перевести процесс работы с заявками из неформального режима в управляемый, прозрачный и измеримый, повысив скорость и качество обслуживания.

---

## 2. Ролевая модель

| Роль | Описание |
|------|----------|
| Пользователь (заявитель) | Создаёт заявки, отслеживает статус, дополняет информацию, оценивает результат. |
| Агент поддержки | Обрабатывает заявки, меняет статусы, ведёт переписку, эскалирует сложные случаи. |
| Руководитель (супервайзер) | Контролирует сроки (SLA), распределяет нагрузку, анализирует отчёты, возвращает заявки на доработку. |
| Администратор системы | Управляет пользователями и ролями, настраивает справочники, правила, аудит. |

---

## 3. Функциональные требования

Система должна:

1. Предоставлять форму создания заявки с обязательными полями «Тема» и «Описание», опциональными «Приоритет», «Категория» и возможностью прикрепления файлов.
2. Автоматически присваивать каждой заявке уникальный номер и фиксировать дату/время создания.
3. Позволять агенту просматривать очередь заявок с фильтрацией по статусам, приоритету, категории и дате.
4. Разрешать агенту брать заявку в работу с автоматическим изменением статуса на «В работе» и фиксацией времени перехода.
5. Поддерживать регламентированные переходы между статусами и блокировать недопустимые переходы.
6. Обеспечивать возможность добавления комментариев к заявке всеми вовлечёнными ролями с привязкой к автору и времени.
7. Позволять руководителю просматривать отчёты по заявкам (количество, среднее время обработки, доля просроченных, оценки пользователей) и выгружать их в CSV/PDF.
8. Давать руководителю возможность переназначать исполнителя и принудительно менять статус в особых случаях с фиксацией причины в журнале аудита.
9. Предоставлять администратору инструменты управления пользователями (добавление, редактирование, удаление, назначение ролей, блокировка) и просмотр журнала действий.
10. Хранить все вложения к заявкам с проверкой типов файлов и ограничением размера, обеспечивая доступ только авторизованным ролям.
11. Уведомлять пользователя об изменении статуса заявки и новых комментариях через интерфейс и (опционально) по электронной почте.

## 4. Нефункциональные требования

### Удобство (usability)
Система должна обеспечивать интуитивно понятный интерфейс для всех ролей: подсказки в полях, выделение обязательных полей, цветовые индикаторы статусов. Пользователь должен создавать заявку и просматривать статус без дополнительного обучения.

### Надёжность (reliability)
Система должна гарантировать доступность не менее 99,5 % времени в рабочие часы. При сбоях данные должны сохраняться в черновике, изменения — фиксироваться транзакционно. Ошибки должны сопровождаться понятными сообщениями для пользователя и технической записью для администратора.

### Производительность (performance)
Система должна отображать список заявок и отчёты не дольше 2 секунд при до 10 000 записей и до 100 одновременных пользователей. Время отклика на создание заявки, изменение статуса или добавление комментария — не более 1 секунды.

### Безопасность (security)
Система должна обеспечивать аутентификацию и разграничение прав по ролям, передачу данных по HTTPS, хранение паролей в хешированном виде. Должен вестись журнал аудита действий, доступный администратору и руководителю.

### Сопровождаемость (maintainability)
Добавление новых типов заявок, статусов или ролей не должно требовать изменения исходного кода: справочники и правила переходов должны управляться через административный интерфейс. Код должен быть структурирован по модулям и сопровождаться документацией.

## 5. Модель данных (сущности и связи)

### Основные сущности

- **Пользователь (User):** id, ФИО, логин, пароль (хеш), роль, email, телефон, статус.
- **Заявка (Request):** id, номер, тема, описание, приоритет, дата создания, дата закрытия, текущий статус, категория, исполнитель, заявитель, SLA.
- **Статус (Status):** id, код, наименование, описание, разрешённые переходы.
- **Категория (Category):** id, название, описание, родительская категория, дефолтный приоритет, ответственная группа.
- **Комментарий (Comment):** id, текст, автор, дата/время, тип, вложения.
- **Вложение (Attachment):** id, имя файла, путь/ссылка, размер, MIME‑тип, владелец, автор загрузки.

### Ключевые связи

- Заявка → Пользователь (заявитель и исполнитель), Категория, Статус.
- К Заявке привязано множество Комментариев и Вложений.
- Статусы связаны правилами переходов (машина состояний).
- Категории могут иметь иерархию.

## 6. Диаграмма вариантов использования (Use Case) — краткое описание

**Актёры:** Пользователь, Агент поддержки, Руководитель, Администратор.  
**Основные сценарии:** создание заявки, просмотр очереди, взятие в работу, изменение статуса, эскалация, назначение исполнителя, отчёты, управление пользователями и справочниками.  
**Связи:** «Взять заявку в работу» включает «Изменить статус заявки»; «Эскалировать заявку» расширяет «Изменить статус заявки».

## 7. Машина состояний заявки (упрощённо)

`Новая` → `В работе` → (`Требуется уточнение` → `В работе`) → `Решена` → `Закрыта`  
Возможен возврат на доработку или эскалация. Все переходы регламентированы.

---

## 8. Критерии приёмки

Система считается соответствующей требованиям, если:

- Пользователь может создать заявку, получить уникальный номер, увидеть её в списке.
- Агент может брать заявки в работу, менять статусы только по разрешённым переходам, добавлять комментарии.
- Руководитель может просматривать отчёты, переназначать исполнителей, контролировать SLA.
- Администратор может управлять пользователями и справочниками, просматривать журнал аудита.
- Интерфейс интуитивно понятен, загрузка списков и отчётов занимает ≤ 2 секунд.
- Данные сохраняются при сбоях, пароли хешированы, права доступа разграничены.
- Добавление новых категорий и правил выполняется через интерфейс без изменения кода.

## 9. Сценарии демонстрации преподавателю

1. **Сценарий «Пользователь создаёт заявку»** (критерии: создание, уникальность, видимость).  
2. **Сценарий «Агент обрабатывает заявку»** (критерии: взятие в работу, статусы, комментарии, эскалация).  
3. **Сценарий «Руководитель контролирует SLA»** (критерии: отчёты, переназначение, контроль сроков).

Для каждого шага указан ожидаемый результат (например: «статус изменился на “В работе”, в журнале аудита появилась запись…»).
